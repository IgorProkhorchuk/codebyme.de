## Що таке сигнал

Сигнал — це асинхронне повідомлення процесу або окремому потоку. Стандартний сигнал повідомляє переважно сам факт події, яку позначає його номер. Джерелом може бути інший процес (`kill`), термінал (Ctrl+C) або ядро. Наприклад, ядро надсилає SIGSEGV після некоректного звернення до пам'яті, а SIGCHLD — коли змінюється стан дочірнього процесу.

Надсилання та доставка — різні моменти. Спочатку сигнал стає **очікуваним** (pending). Ядро доставляє його, коли потік повертається в режим користувача і сигнал не заблокований. Тоді відбувається одне з трьох: виконується дія за замовчуванням, сигнал ігнорується або запускається обробник програми.

Для обробника ядро зберігає контекст потоку й передає керування функції. Після її завершення системний виклик `sigreturn` відновлює контекст. Тому обробник може вклинитися майже будь-де, зокрема посеред оновлення структури даних. Звідси більшість труднощів із сигналами.

## Сигнали, які варто знати

У скриптах і коді звертайтеся до сигналів за іменами, бо номери частини з них залежать від архітектури та операційної системи. У таблиці наведено номери для Linux на x86 та ARM.

| № | Сигнал | Коли виникає або для чого потрібен | Дія за замовчуванням |
| --- | --- | --- | --- |
| 1 | SIGHUP | Розрив із керівним терміналом; демони часто перечитують за ним конфігурацію | Завершення |
| 2 | SIGINT | Ctrl+C | Завершення |
| 3 | SIGQUIT | Ctrl+\\ | Завершення + core dump |
| 7 | SIGBUS | Помилка доступу до пам'яті | Завершення + core dump |
| 9 | SIGKILL | Примусове завершення | Завершення |
| 10 | SIGUSR1 | Визначає сама програма | Завершення |
| 11 | SIGSEGV | Некоректне звернення до пам'яті | Завершення + core dump |
| 12 | SIGUSR2 | Визначає сама програма | Завершення |
| 13 | SIGPIPE | Запис у pipe, який ніхто не читає | Завершення |
| 15 | SIGTERM | Прохання завершитися | Завершення |
| 17 | SIGCHLD | Дочірній процес завершився, зупинився або відновився | Ігнорування |
| 18 | SIGCONT | Відновлення зупиненого процесу | Продовження |
| 19 | SIGSTOP | Примусова зупинка | Зупинка |
| 20 | SIGTSTP | Ctrl+Z | Зупинка |
| 28 | SIGWINCH | Змінився розмір вікна термінала | Ігнорування |

У довідниках можна побачити інші номери. Наприклад, у BSD та macOS SIGBUS має номер 10, SIGSTOP — 17, SIGTSTP — 18, SIGCONT — 19, SIGUSR1 — 30, а SIGUSR2 — 31. Свою систему перевірте командою `kill -l`. Створення core dump також залежить від налаштувань, зокрема від `ulimit -c`: дія «core» ще не гарантує, що файл з'явиться.

**SIGKILL і SIGSTOP не можна перехопити, заблокувати чи проігнорувати.** SIGCONT має особливість: зупинений процес відновиться, навіть якщо програма блокує або ігнорує цей сигнал. Блокування лише відкладає запуск обробника.

SIGTERM дає програмі шанс закрити з'єднання, скинути буфери та завершити поточну роботу. SIGKILL такого шансу не дає, тому `kill -9` варто залишати на випадок, коли коректне завершення не спрацювало. Ядро все одно звільнить пам'ять і закриє дескриптори, але незавершену логіку програми ніхто не виконає.

## Як правильно обробляти сигнали

Надійний обробник робить якнайменше: запам'ятовує, що сигнал прийшов, а решту залишає основному коду. Уявіть, що сигнал перервав `printf` або `malloc`, коли ті змінювали внутрішній стан чи тримали блокування. Якщо обробник викличе ту саму функцію, можна отримати пошкоджені дані або deadlock. Тому в асинхронному обробнику безпечно викликати лише async-signal-safe функції. Їх перелік є в [signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html): `write` там є, а `printf` і `malloc` немає.

Для встановлення обробника в C використовуйте `sigaction`: її поведінка визначена чіткіше й переносніше, ніж у `signal`.

```c
#define _POSIX_C_SOURCE 200809L
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

static volatile sig_atomic_t stop_requested = 0;

static void on_stop(int signo) {
    (void)signo;
    stop_requested = 1;
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = on_stop;
    sigemptyset(&sa.sa_mask);

    if (sigaction(SIGTERM, &sa, NULL) == -1 ||
        sigaction(SIGINT, &sa, NULL) == -1) {
        perror("sigaction");
        return 1;
    }

    printf("PID: %ld\n", (long)getpid());
    fflush(stdout);

    while (!stop_requested) {
        sleep(1); /* тут була б корисна робота */
    }

    puts("Завершуємо роботу коректно");
    return 0;
}
```

Тип `volatile sig_atomic_t` підходить для такого прапорця між обробником і перерваним ним кодом. Для синхронізації потоків він не призначений.

### Перервані системні виклики

Якщо обробник спрацював під час блокувального виклику, той може повернути помилку `EINTR`. Прапорець `SA_RESTART` просить ядро автоматично перезапустити виклик, але діє не всюди. Наприклад, `poll`, `epoll_wait` і `nanosleep` після обробника не перезапускаються. Крім того, `read` або `write` можуть встигнути передати лише частину даних. Надійний код враховує обидва випадки.

У прикладі `SA_RESTART` немає навмисно: так перерваний виклик повертає керування, і програма може перевірити прапорець. Але сам прапорець не усуває гонку, коли сигнал приходить між перевіркою та блокувальним викликом. Тут цикл просто прокинеться щонайбільше приблизно за секунду. Виклик без тайм-ауту міг би чекати безкінечно, тому для нього потрібні `sigsuspend`, `ppoll`, `signalfd` або self-pipe.

### Маски, черги та потоки

**Блокування й ігнорування — різні речі.** Заблокований сигнал чекає, доки його розблокують. Проігнорований за звичайних умов просто відкидається.

Стандартні сигнали не накопичуються в черзі. Якщо SIGUSR1 заблокований і надісланий п'ять разів, очікуваним буде лише один екземпляр. Отже, лічити події стандартними сигналами не можна. Сигнали реального часу (від `SIGRTMIN` до `SIGRTMAX`) стають у чергу, мають гарантований порядок і через `sigqueue` можуть нести невелике значення. Черга при цьому обмежена.

У багатопотоковій програмі дії для сигналів спільні для всього процесу, а маска в кожного потоку своя. Сигнал, адресований процесу, може отримати будь-який потік, який його не блокує. Поширене рішення: заблокувати потрібні сигнали до створення потоків і приймати їх в одному виділеному потоці через `sigwaitinfo` або `sigwait`.

Під час `fork` дочірній процес успадковує дії та маску, але не очікувані сигнали. Після `execve` перехоплені сигнали повертаються до дії за замовчуванням. Проігноровані залишаються проігнорованими, а маска й очікувані сигнали зберігаються.

## Сигнали на практиці

### Командний рядок

Команда `kill` насправді надсилає сигнали, а не обов'язково «вбиває». Без явно вказаного сигналу вона надсилає SIGTERM.

```bash
kill 1234               # SIGTERM
kill -HUP 1234          # часто: перечитати конфігурацію
kill -STOP 1234         # зупинити
kill -CONT 1234         # відновити
kill -TERM -- -1234     # сигнал усій групі процесів 1234
kill -0 1234            # сигнал не надсилається, лише перевірка
```

SIGHUP перечитує конфігурацію лише там, де програма це реалізувала, тому спершу загляньте в її документацію. Успішний `kill -0` означає, що ціль існує і ви маєте право їй сигналити. Помилка ще не доводить, що процесу немає: можливо, бракує прав.

У shell-скриптах сигнали перехоплює `trap`. Bash відкладає виконання trap, поки працює команда на передньому плані. Тому довгу роботу зручно запускати у фоні й чекати через `wait`:

```bash
#!/usr/bin/env bash
child=

shutdown() {
    trap '' TERM INT
    if [[ -n $child ]]; then
        kill -TERM "$child" 2>/dev/null
        wait "$child"
    fi
    exit 0
}

trap shutdown TERM INT

sleep 300 &
child=$!
wait "$child"
```

Цей приклад пересилає сигнал лише прямому дочірньому процесу. Якщо той створює власні процеси, подбайте і про них. Коли Bash повідомляє, що команду завершив сигнал N, її статус дорівнює 128 + N. Тому 137 зазвичай означає SIGKILL, а 143 — SIGTERM. Проте програма може й сама вийти з таким кодом. І навіть справжній SIGKILL ще не доводить, що спрацював OOM killer.

### systemd і контейнери

Під час зупинки сервісу systemd за типових налаштувань надсилає SIGTERM процесам його cgroup. Якщо вони не завершилися за відведений час, надходить SIGKILL. Цю поведінку змінюють `KillSignal=`, `KillMode=` і `TimeoutStopSec=`.

`docker stop` спершу надсилає головному процесу сигнал зупинки (типово SIGTERM, але образ чи контейнер можуть задати інший). Після тайм-ауту Docker надсилає SIGKILL.

У контейнері головний процес зазвичай має PID 1 у своєму PID namespace, а для нього діють особливі правила. Сигнал із того самого namespace, для якого PID 1 не встановив обробник, не виконає звичну дію за замовчуванням. SIGKILL і SIGSTOP із батьківського namespace при цьому діють. Тому програма без обробника SIGTERM може чекати весь тайм-аут і лише потім загинути від SIGKILL.

Ще одна пастка — shell-обгортка, яка залишається PID 1 і не пересилає сигнали застосунку. Якщо скрипт лише готує середовище, завершуйте його через `exec`:

```sh
#!/bin/sh
# підготовка середовища
exec "$@"
```

Тоді застосунок замінить shell і отримає його PID. Обробляти сигнали він усе одно повинен сам. Якщо потрібно ще й прибирати zombie-процеси та пересилати сигнали, допоможе невеликий init, наприклад `docker run --init`.

### Коли процес не реагує

Маски та дії для сигналів видно в `/proc`:

```bash
grep -E '^(State|SigPnd|ShdPnd|SigBlk|SigIgn|SigCgt):' /proc/1234/status
```

`SigBlk`, `SigIgn` і `SigCgt` показують заблоковані, проігноровані та перехоплені сигнали, а `SigPnd` і `ShdPnd` — очікувані для потоку та всього процесу. Це шістнадцяткові бітові маски: сигналу N відповідає біт N−1. Наприклад, `0000000000004000` означає SIGTERM (15). Спостерігати за доставкою наживо можна через `strace -f -p 1234`.

Навіть SIGKILL не завжди спрацьовує миттєво. Процес у стані `D` (uninterruptible sleep), наприклад під час проблем з I/O, може не завершитися, доки не вийде з очікування в ядрі. Деякі такі очікування все ж переривають фатальні сигнали. Zombie (`Z`) уже завершився, тож вбивати його нема чого. Запис зникне, коли батьківський процес викличе `wait`. Якщо батько завершиться, це зробить новий батьківський процес.

## Підсумок

- Для зупинки спершу надсилайте SIGTERM і давайте процесу час. SIGKILL — крайній засіб.
- В обробнику лише фіксуйте подію, а роботу виконуйте в основному коді.
- Не рахуйте події стандартними сигналами.
- Враховуйте `EINTR`, часткове читання та запис.
- У контейнері перевірте, хто є PID 1 і чи доходить сигнал до застосунку.

Перевірте свій сервіс: надішліть йому SIGTERM під навантаженням. Подивіться, чи завершив він поточні запити, скільки часу це зайняло і з яким статусом він вийшов. Так ви дізнаєтеся, як він насправді зупиняється.
