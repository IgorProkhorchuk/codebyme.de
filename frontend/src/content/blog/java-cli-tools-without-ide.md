Є така ситуація, знайома кожному збоченцю, хто хоч раз пробував писати на Java без IDE, у Vim чи в іншому текстовому редакторі. 
Ти пишеш код, і тобі потрібно згадати, які методи є в класі `Math`. 
Або яка саме сигнатура в якогось методу. 
В IntelliJ можна натиснути `Ctrl+Space` або навести курсор на ім'я, і з'явилася б підказка з Javadoc. 
Логічно, що в редакторі без автокомпліту такої підказки немає.

## Як подивитися, що є в класі

### `javap`: дизасемблер, який є в кожному JDK

Коли Java-код компілюється, з `.java` файлу виходить `.class` файл: це байткод, який виконує віртуальна машина. Інструмент `javap` робить обернену річ: бере `.class` файл і показує, що в ньому лежить. Тому його й називають дизасемблером.

Для такої задачі найкорисніше те, що `javap` показує **сигнатури** всіх полів і методів класу. Тобто саме те, що ми звикли бачити у підказках IDE: назви, типи параметрів, типи значень, що повертаються, модифікатори доступу.

Це він вміє робити не лише для ваших власних класів, а й для класів самого JDK. Тобто можна подивитися, що всередині `java.lang.Math`, `java.util.ArrayList` чи будь-якого іншого стандартного класу.

У `javap` багато можливостей (наприклад, він може показати власне байткod інструкцій), але для щоденного використання достатньо базового режиму.

> Невеликий практичний нюанс. Для стандартних класів JDK `javap` вміє знаходити їх і за повним іменем, без жодних файлів, наприклад `javap java.lang.Math`.

### Де взагалі лежать класи JDK: `jimage`

Починаючи з Java 9, стандартна бібліотека живе не в старому добре відомому `rt.jar`, а в спеціальному файлі `lib/modules`. Це оптимізований контейнер у власному форматі, і відкрити його звичайним архіватором не вийде. Для роботи з ним у JDK є утиліта `jimage`.

Вона вміє дві корисні речі.

**Перша: показати вміст.** Команда `jimage list` виводить список усіх класів та ресурсів, що лежать у файлі. Список величезний, тому його зручно фільтрувати через `grep`. Наприклад, шукаємо все, що має відношення до `math`:

```bash
jimage list /usr/lib/jvm/java-25-openjdk-amd64/lib/modules | grep -i math
```

У виводі одразу видно і `java/lang/Math.class`, і `java/lang/StrictMath.class`, і весь пакет `java/math` з `BigDecimal`, `BigInteger`, `MathContext`, `RoundingMode`. Заодно видно і внутрішні класи на кшталт `jdk/internal/math/DoubleToDecimal.class`, які є деталлю реалізації, але на них цікаво глянути.

Шлях до файлу `modules` залежить від вашої системи та способу встановлення JDK. У моєму випадку це `/usr/lib/jvm/java-25-openjdk-amd64/lib/modules`.

**Друга: витягти все на диск.** Команда `jimage extract` розпаковує вміст у поточну директорію:

```bash
mkdir jvm_analysis && cd jvm_analysis
jimage extract /usr/lib/jvm/java-25-openjdk-amd64/lib/modules
```

Після цього в папці з'являється набір директорій, по одній на кожен модуль JDK: `java.base`, `java.sql`, `java.desktop`, `java.net.http`, `jdk.compiler` та інші. Всередині кожної лежать пакети та `.class` файли у звичній структурі каталогів.

Тепер у нас є звичайні файли на диску, і з ними можна працювати звичайними інструментами.

### Збираємо все разом

Далі все просто. Шукаємо потрібний клас через `find`:

```bash
find . -iname "Math*"
```

У результаті бачимо `./java.base/java/lang/Math.class`, а також кілька схожих за назвою файлів, серед яких `MathContext.class` та `MathUtils.class`.

І віддаємо знайдений файл у `javap`:

```bash
javap -p ./java.base/java/lang/Math.class
```

Прапорець `-p` каже показувати також приватні члени. Без нього `javap` виводить тільки публічні та захищені, що для більшості випадків якраз і потрібно. Але з `-p` можна побачити внутрішню кухню класу.

Результат виглядає так:

```
Compiled from "Math.java"

  public static final double E;
  public static final double PI;
  public static final double TAU;
  private static final double DEGREES_TO_RADIANS;
  private static final double RADIANS_TO_DEGREES;
  ...
  public static double sin(double);
  public static double cos(double);
  public static double tan(double);
  public static double asin(double);
  public static double acos(double);

```

Тобто ми отримали повний перелік констант і методів класу `Math` з усіма типами, не відкриваючи ні браузер, ні IDE. Цікавий бонус: у цьому списку видно, що в Java 25 в `Math` є константа `TAU` (це 2π), якої багато хто навіть не помічав.

Чого тут немає, так це текстів Javadoc: `.class` файли їх не зберігають, коментарі при компіляції відкидаються. Але для головної задачі, тобто згадати назву й сигнатуру методу, цього цілком достатньо.

## Частина 2. Інструменти для аналізу працюючої JVM

Оце навіть цікавіша частина. Той самий JDK, який допомагає читати класи, містить цілий набір утиліт для діагностики запущених Java-програм. Основні з них такі:

- **`jps`** показує, які Java-процеси зараз запущені;
- **`jstat`** показує статистику роботи JVM, насамперед збирача сміття (GC);
- **`jstack`** робить знімок усіх потоків і того, що вони зараз роблять;
- **`jmap`** працює з пам'яттю: показує, які об'єкти займають купу, і вміє зберігати її дамп;
- **`jcmd`** універсальний інструмент, який вміє надсилати JVM різні команди, і багато чого з перерахованого вище.

Кожен із них заслуговує окремої статті, тому тут покажу лише базові сценарії.

### `jps`: знайти потрібний процес

Щоб щось діагностувати, треба знати ідентифікатор процесу (PID). `jps` це і робить:

```bash
jps -l
```

Прапорець `-l` показує повне ім'я головного класу або шлях до jar-файлу, а не лише коротку назву. Виглядає це так:

```
120903 jdk.jcmd/sun.tools.jps.Jps
108646 DeadlockExample
```

Перший рядок це сам `jps` (він теж Java-програма, тож бачить сам себе). Другий це моя тестова програма `DeadlockExample` з PID 108646. Саме цей номер знадобиться всім іншим інструментам.

### Приклад: програма, яка зависла

Щоб показати, як усе це працює на практиці, я написав навмисно зламану програму. Це класичний приклад **deadlock** (взаємного блокування). Два потоки беруть два замки (локи) у протилежному порядку:

- перший потік бере замок A і намагається взяти замок B;
- другий потік бере замок B і намагається взяти замок A.

Якщо обидва встигли взяти по своєму першому замку, то далі вони чекатимуть один на одного вічно. Програма не падає, не виводить помилок: вона просто стоїть. Саме такі проблеми найважче ловити «на око».

Мінімальна версія такої програми виглядає приблизно так (я наводжу спрощений варіант, щоб було зрозуміло принцип):

```java
public class DeadlockExample {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                pause();
                synchronized (lockB) {
                    System.out.println("Thread-1 done");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                pause();
                synchronized (lockA) {
                    System.out.println("Thread-2 done");
                }
            }
        });

        t1.start();
        t2.start();
    }

    private static void pause() {
        try { Thread.sleep(500); } catch (InterruptedException ignored) {}
    }
}
```

Пауза між першим і другим замком потрібна, щоб обидва потоки гарантовано встигли взяти по першому замку, перш ніж намагатися взяти другий.

Запускаємо програму, вона зависає. Тепер дивимося, що з нею.

### `jstack`: знімок усіх потоків

Беремо PID з `jps` і викликаємо:

```bash
jstack 108646
```

Утиліта виводить стан усіх потоків процесу: і ваших, і службових (наприклад, потоки збирача сміття на кшталт `GC Thread#0`). Більша частина виводу це довгий перелік потоків, але в самому кінці `jstack` робить одну дуже корисну річ: він сам перевіряє, чи немає взаємних блокувань, і якщо є, то виводить окремий розділ:

```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x00007ba794002630 (object 0x0000000714613f70, a java.lang.Object),
  which is held by "Thread-2"

"Thread-2":
  waiting to lock monitor 0x00007ba788000f60 (object 0x0000000714613f60, a java.lang.Object),
  which is held by "Thread-1"
```

Читається це майже як людська мова. `Thread-1` чекає на замок, який тримає `Thread-2`. А `Thread-2` чекає на замок, який тримає `Thread-1`. Це і є замкнене коло.

Нижче `jstack` показує стеки викликів обох потоків, і саме там видно, **де в коді** все сталося:

```
"Thread-1":
        at DeadlockExample.lambda$main$0(DeadlockExample.java:25)
        - waiting to lock <0x0000000714613f70> (a java.lang.Object)
        - locked <0x0000000714613f60> (a java.lang.Object)
        ...
"Thread-2":
        at DeadlockExample.lambda$main$1(DeadlockExample.java:47)
        - waiting to lock <0x0000000714613f60> (a java.lang.Object)
        - locked <0x0000000714613f70> (a java.lang.Object)
        ...
Found 1 deadlock.
```

Тут варто придивитися до адрес об'єктів. `Thread-1` вже тримає замок `...f60` і чекає на `...f70`. `Thread-2` навпаки: тримає `...f70` і чекає на `...f60`. Крім того, `jstack` називає точні рядки коду: 25 і 47 у файлі `DeadlockExample.java`. Тобто з одного виводу можна знайти і причину, і місце в коді, куди йти виправляти.

Найприємніше те, що весь цей аналіз зроблено над живою програмою, без перезапуску, без дебагера і без IDE. Тільки PID і одна команда.

### коротко про `jstat`, `jmap`, `jcmd`

Ось що вони вміють у базових сценаріях.

**`jstat`** вміє періодично друкувати статистику збирача сміття. Наприклад, `jstat -gcutil <pid> 1000` кожну секунду показує, наскільки заповнені різні області пам'яті і скільки часу пішло на збирання сміття. Це швидкий спосіб зрозуміти, чи не страждає програма від частих пауз GC.

**`jmap`** працює з купою (heap). Команда `jmap -histo <pid>` показує гістограму: які класи мають скільки екземплярів і скільки місця вони займають. Для пошуку витоків пам'яті це часто перший крок. А `jmap -dump:format=b,file=heap.hprof <pid>` зберігає повний дамп пам'яті у файл, який потім можна проаналізувати у спеціальних програмах, наприклад у Eclipse MAT.

**`jcmd`** це свого роду швейцарський ніж. Він надсилає працюючій JVM «діагностичні команди». Список доступних команд можна подивитися через `jcmd <pid> help`. Багато з того, що роблять `jstack` та `jmap`, доступне і через `jcmd`: наприклад, `jcmd <pid> Thread.print` дає те саме, що й `jstack`, а `jcmd <pid> GC.heap_info` показує інформацію про купу. У сучасних версіях JDK `jcmd` вважається основним інструментом, а старіші утиліти поступово відходять на другий план. Тому якщо вчити щось одне, то варто починати саме з нього.

## Підсумок

Щоб **читати сигнатури класів**, використовуємо зв'язку `jimage` і `javap`: `jimage list` допомагає знайти клас, `jimage extract` дістає файли на диск, а `javap -p` показує все, що в класі є.

Щоб **діагностувати працюючу програму**, використовуємо `jps` для пошуку процесу та `jstack`, `jstat`, `jmap` і `jcmd` для розбору конкретних проблем: зависань, пауз збирача сміття, витоків пам'яті.

Усе це вже встановлено разом із JDK, нічого додатково ставити не треба.
