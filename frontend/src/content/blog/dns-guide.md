Ви вводите `https://codebyme.de` у браузері. Перш ніж встановити з’єднання із сайтом, браузер має з’ясувати, куди його встановлювати. Зазвичай для цього потрібно перетворити доменне ім’я на IP-адресу. Цю задачу вирішує **DNS — Domain Name System**.

Але DNS — це не один сервер із переліком усіх сайтів. Це розподілена система: клієнт на вашому пристрої, кеші, рекурсивний resolver та сервери, відповідальні за різні частини простору імен. Браузер також може використовувати власний DNS, оминаючи resolver операційної системи.

Розберемо шлях запиту, типи записів, налаштування комп’ютера й роутера, шифрування та перевірку результату. Для читання достатньо розуміти IP-адресу й мережевий інтерфейс; [IPv4 і підмережі](/blog/ipv4-subnetting-guide) розглянуті окремо.

## Що саме робить DNS

У URL `https://codebyme.de/blog` є схема `https`, ім’я хоста `codebyme.de` та шлях `/blog`. DNS працює з іменем хоста. Він не шукає статтю `/blog` і не передає браузеру її HTML.

Після отримання адреси браузер окремо встановлює з’єднання, узгоджує TLS та обмінюється HTTP-повідомленнями. Для HTTP/3 використовується QUIC, для HTTP/1.1 та HTTP/2 зазвичай TCP. Успішний DNS-запит ще не означає, що сервер доступний або його TLS-сертифікат правильний.

Відповідність між іменами й адресами не обов’язково взаємно однозначна:

- Одне ім’я може мати кілька IPv4- та IPv6-адрес: для балансування, резервування або CDN.
- Багато імен можуть вести на одну адресу. Сервер розрізняє потрібний сайт за інформацією в TLS та HTTP.
- Відповіді можуть відрізнятися залежно від часу, resolver і мережевого розташування.

DNS також публікує поштові маршрути, перевірки володіння доменом і параметри сервісів. Пошук IP-адреси — лише найпомітніший випадок його використання.

## Що називають DNS-сервером

У налаштуваннях мережі «DNS server» зазвичай означає адресу **рекурсивного resolver** або локального посередника до нього. Це не той самий сервер, де ви редагуєте записи власного домену.

| Учасник | Задача |
| --- | --- |
| Stub resolver | Клієнтська частина на пристрої: передає запити й отримує відповіді |
| Рекурсивний resolver | Знаходить відповідь для клієнта, звертаючись до інших серверів і використовуючи кеш |
| DNS-forwarder | Передає запити іншому resolver; часто працює на домашньому роутері |
| Root server | Допомагає знайти сервери доменів верхнього рівня, наприклад `.de` |
| TLD server | Допомагає знайти авторитетні сервери домену в зоні, наприклад `example.net` у `.net` |
| Авторитетний сервер | Відповідає на підставі даних DNS-зони, за яку відповідає |

Серверне ПЗ може виконувати кілька ролей, але логічно їх варто розрізняти. Публічний resolver не стає власником зони, коли кешує її записи.

Адреса `192.168.1.1` у полі DNS часто означає: «запитуй роутер, а він перешле запит далі». Адреса `127.0.0.53` на Linux із `systemd-resolved` означає локальний stub listener, а не зовнішній сервер.

Ієрархію та формати DNS описують [RFC 1034](https://www.rfc-editor.org/rfc/rfc1034) і [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035).

## Шлях запиту і кешування

Припустімо, клієнту потрібен запис `A` для `www.example.net`, а потрібних даних немає в кеші. Нижче — спрощений сценарій; адреса відповіді умовна.

![Клієнт звертається до рекурсивного resolver. Той отримує делегування від root і .net, а потім відповідь від авторитетного сервера example.net](/blog-images/dns-resolution.svg)

1. Клієнт просить resolver знайти відповідь. Це **рекурсивний запит**: клієнт очікує результат або помилку, а не перелік серверів для самостійного обходу.
2. Resolver звертається до кореневого сервера й отримує делегування до `.net`.
3. Сервер `.net` вказує авторитетні сервери `example.net`.
4. Авторитетний сервер повертає потрібний запис або іншу відповідь: наприклад, `CNAME` чи повідомлення про відсутність імені.
5. Resolver повертає результат клієнту та кешує дані відповідно до їхнього TTL.

Між resolver та серверами ієрархії це зазвичай **ітеративний пошук**. Кореневий сервер не звертається до `.net` замість resolver. У реальній мережі кеш делегувань дозволяє пропускати частину кроків. QNAME minimization може також обмежувати, яку частину імені бачить кожен рівень.

Подивитися делегування можна через `dig`:

```bash
dig +trace codebyme.de A
```

`dig +trace` сам проходить ієрархію. Це не журнал запитів вашого звичайного resolver і не перевірка DoH браузера. У мережі, яка дозволяє DNS лише через внутрішній resolver, команда може не працювати.

### TTL і негативне кешування

**TTL — Time To Live**, час кешування в секундах. Якщо запис отримано з TTL `300`, кеш зазвичай може використовувати його протягом наступних п’яти хвилин. У відповіді кешувального resolver ви часто бачите вже залишок цього часу.

```bash
dig codebyme.de A +noall +answer
```

Щоб читати результат, корисно розкласти одну відповідь. Нижче **умовний скорочений вивід**, а не поточні дані реального домену:

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0
;; QUESTION SECTION:
;www.example.net.       IN A
;; ANSWER SECTION:
www.example.net. 187    IN A 203.0.113.10
;; Query time: 12 msec
;; SERVER: 192.0.2.53#53(192.0.2.53) (UDP)
```

Тут `NOERROR` — код результату, `187` — TTL у секундах, `IN` — клас Internet, `A` — тип, а `203.0.113.10` — дані запису. `rd` означає запитану рекурсію, `ra` — повідомлення сервера, що рекурсія доступна. `SERVER` — адресат саме цього запиту, а не обов’язково авторитетний сервер домену. Адреса `192.0.2.53` також узята з документаційного діапазону.

Зміна запису в панелі DNS-провайдера не очищає кеші всіх клієнтів. Перед перенесенням сайту TTL зменшують **заздалегідь**: уже закешована відповідь продовжує жити за попереднім TTL. Водночас сервер має прийняти оновлену зону — TTL не виправить помилку її публікації.

Кешуються й негативні відповіді. Якщо ім’я не існувало, щойно створений запис може ще деякий час залишатися невидимим для resolver, який зберіг попередню відповідь. Правила визначає [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308). Деякі resolver також можуть тимчасово повертати прострочені дані при збоях upstream: це окремий механізм serve-stale, а не «нескінченний TTL».

## Записи, зони й делегування

Запит визначається не лише ім’ям, а й типом запису. `A example.net` і `MX example.net` — різні питання.

| Тип | Що визначає |
| --- | --- |
| `A` | IPv4-адресу |
| `AAAA` | IPv6-адресу |
| `CNAME` | Інше доменне ім’я — канонічну ціль псевдоніма |
| `MX` | Поштові сервери та їхні пріоритети |
| `TXT` | Текстові дані: зокрема SPF, DKIM і перевірки володіння |
| `NS` | Авторитетні сервери зони та делегування |
| `SOA` | Метадані зони: серійний номер і параметри її обслуговування |
| `PTR` | Ім’я в просторі зворотного DNS |
| `CAA` | Які центри сертифікації можуть видавати сертифікати |
| `HTTPS`, `SVCB` | Прив’язку сервісу та параметри підключення |

Умовний фрагмент зони:

```dns
$ORIGIN example.net.
$TTL 300
@       IN A     203.0.113.10
@       IN AAAA  2001:db8::10
www     IN CNAME example.net.
@       IN MX    10 mail.example.net.
mail    IN A     203.0.113.20
```

Це ілюстрація, а не готова зона: тут немає обов’язкових `SOA` та `NS`. Адреси `203.0.113.0/24` і `2001:db8::/32` призначені для документації. Крапка наприкінці `example.net.` означає абсолютне ім’я; без неї файловий формат зони може дописати поточний `$ORIGIN`.

`CNAME` не є HTTP-редиректом. Він допомагає знайти DNS-дані іншого імені, але не змінює URL у браузері. Звичайний `CNAME` також не можна довільно поєднувати з іншими даними на тому самому імені. «CNAME flattening» у панелях провайдерів — окрема можливість реалізації.

**Зона** — частина DNS-простору під певним адміністративним керуванням. Піддомен не обов’язково є окремою зоною: `blog.example.net` може залишатися записом у зоні `example.net`. Для окремого керування його можна делегувати іншими `NS`; за потреби публікуються glue-записи адрес серверів.

Реєстратор домену й DNS-хостинг можуть бути різними компаніями. Зміна `NS` у реєстратора змінює делегування, а зміна DNS у Wi-Fi на ноутбуці — лише те, кого ноутбук запитуватиме.

Для IPv4 зворотні записи розміщені в `in-addr.arpa`, для IPv6 — в `ip6.arpa`. Власник IP-простору часто керує ними окремо від власника прямої зони. Відсутність `PTR` не означає, що запис `A` неправильний.

Записи `HTTPS/SVCB`, визначені в [RFC 9460](https://www.rfc-editor.org/rfc/rfc9460), можуть повідомляти підтримувані протоколи й параметри сервісу. Вони не замінюють перевірку TLS-сертифіката.

## Звідки система бере DNS

За типової домашньої конфігурації пристрій отримує параметри автоматично. Для IPv4 DNS часто передається через DHCP. В IPv6 джерелами можуть бути Router Advertisement з RDNSS та DHCPv6.

У результаті система може знати кілька resolver: від Ethernet, Wi-Fi та VPN. Це не завжди один глобальний список. Наприклад, запити до `corp.example` можуть спрямовуватися у VPN, а решта — до домашньої мережі. Це **split DNS**.

На визначення імен впливають також:

- `hosts`: локальні відповідності імен адресам;
- правила системного name service, наприклад `/etc/nsswitch.conf` у Linux;
- mDNS для локального виявлення, зокрема імен `.local`;
- кеші операційної системи й програм;
- власний resolver браузера та його DoH-політики.

Універсальна схема «спочатку hosts, потім кеш, потім DNS» недостатня для всіх програм. Наприклад, `dig` робить DNS-запит і не є тестом того, що поверне системний `getaddrinfo()` з урахуванням усіх локальних механізмів.

## Як подивитися поточну конфігурацію

Спочатку з’ясуйте, що вже налаштовано. Команди цього розділу нічого не змінюють. `dig` постачається, наприклад, у пакетах `dnsutils` або `bind-utils`; назва залежить від дистрибутива. На Windows використовуйте PowerShell-аналоги нижче.

### Linux

Якщо використовується `systemd-resolved`:

```bash
resolvectl status
```

Дивіться DNS-сервери **кожного інтерфейсу**, поточний сервер і routing domains. Позначення `~corp.example` означає домен маршрутизації DNS, а `~.` — кореневий routing domain для запитів без більш специфічного маршруту. Вибір залежить від конфігурації всіх інтерфейсів.

Запит через `systemd-resolved`:

```bash
resolvectl query codebyme.de
```

У системах із glibc перевірка через механізм NSS:

```bash
getent ahosts codebyme.de
```

Перевірка файлу сумісності та його цілі:

```bash
ls -l /etc/resolv.conf
cat /etc/resolv.conf
```

Якщо там `127.0.0.53`, це ще не відповідь на питання «який зовнішній resolver використовується». Дивіться `resolvectl status`. Режими файлу описані в [документації systemd-resolved](https://www.freedesktop.org/software/systemd/man/latest/systemd-resolved.service.html).

### Windows

У PowerShell:

```powershell
Get-DnsClientServerAddress | Format-Table InterfaceAlias, AddressFamily, ServerAddresses -AutoSize
```

Запит із використанням поточної конфігурації:

```powershell
Resolve-DnsName codebyme.de -Type A
```

### macOS

Поточна конфігурація системних resolver, включно зі scoped resolver:

```bash
scutil --dns
```

Перелік мережевих сервісів:

```bash
networksetup -listallnetworkservices
```

Ручні DNS-параметри конкретного сервісу:

```bash
networksetup -getdnsservers "Wi-Fi"
```

Відсутність вручну заданих DNS не означає, що DNS не працює: сервери можуть надходити автоматично. Ефективну картину дивіться через `scutil --dns`.

### Запит до конкретного сервера

На системі з `dig`:

```bash
dig @1.1.1.1 codebyme.de A
```

У PowerShell:

```powershell
Resolve-DnsName codebyme.de -Type A -Server 1.1.1.1 -DnsOnly
```

Ці команди **не змінюють** DNS для інших програм. У `dig` поле `SERVER` показує адресата запиту: якщо це локальний forwarder, воно не показує, до кого він звертався далі.

## Як змінити DNS у системі та роутері

Нижче стандартний resolver Cloudflare використовується як конкретний приклад, а не вимога обрати саме його. Збережіть поточні налаштування. Корпоративний VPN та внутрішні домени можуть потребувати корпоративного DNS.

### Linux: NetworkManager

Знайдіть назву активного профілю:

```bash
nmcli connection show --active
```

Замініть `My Wi-Fi` на точну назву **профілю з’єднання**, яка не обов’язково збігається з іменем інтерфейсу на кшталт `wlp2s0`.

Для IPv4:

```bash
sudo nmcli connection modify "My Wi-Fi" ipv4.ignore-auto-dns yes ipv4.dns "1.1.1.1 1.0.0.1"
```

За наявності робочого IPv6 налаштуйте його DNS також:

```bash
sudo nmcli connection modify "My Wi-Fi" ipv6.ignore-auto-dns yes ipv6.dns "2606:4700:4700::1111 2606:4700:4700::1001"
```

Застосуйте профіль. Це може короткочасно перервати з’єднання:

```bash
sudo nmcli connection up "My Wi-Fi"
```

`ignore-auto-dns` не переводить DHCP-адресу на статичну. Перевірте результат через `resolvectl status` або засоби вашого resolver. Активний VPN може продовжувати застосовувати свої DNS-маршрути.

Повернення до автоматичних DNS, **якщо до експерименту не було власного ручного списку**:

```bash
sudo nmcli connection modify "My Wi-Fi" ipv4.ignore-auto-dns no ipv4.dns "" ipv6.ignore-auto-dns no ipv6.dns ""
sudo nmcli connection up "My Wi-Fi"
```

Попередню ручну конфігурацію відновіть зі збережених значень. Властивості описані в [NetworkManager Reference Manual](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/nm-settings-nmcli.html).

### Linux: systemd-resolved

`systemd-resolved` обслуговує визначення імен, а джерелом постійної конфігурації часто є NetworkManager або `systemd-networkd`. Не варто одночасно редагувати всі можливі місця.

Тимчасовий експеримент для інтерфейсу `enp3s0`:

```bash
sudo resolvectl dns enp3s0 1.1.1.1 1.0.0.1
sudo resolvectl domain enp3s0 '~.'
resolvectl status enp3s0
```

Це тимчасові параметри: мережевий менеджер, перепідключення або перезавантаження можуть їх замінити. Більш специфічні DNS-маршрути VPN вони також не скасовують.

Скидання тимчасових per-link параметрів:

```bash
sudo resolvectl revert enp3s0
```

Після скидання перевірте стан; за потреби перепідключіть профіль, щоб менеджер знову передав автоматичні параметри. `revert` не є збереженою копією попередньої конфігурації.

Якщо `/etc/resolv.conf` генерується автоматично або є симлінком, ручне додавання `nameserver` у нього буде ненадійним. Змінюйте джерело конфігурації, яке реально керує DNS.

### Windows

У Windows 11: **Settings → Network & internet → Wi-Fi або Ethernet → властивості потрібного підключення → DNS server assignment → Edit**. Виберіть ручне призначення й внесіть адреси. Для Wi-Fi спочатку може знадобитися відкрити властивості вибраної мережі.

Не плутайте це з призначенням IP-адреси: DHCP може залишатися увімкненим, а DNS бути ручним. Назви елементів залежать від версії та локалізації; актуальні кроки є в [довідці Microsoft](https://support.microsoft.com/en-us/windows/experience/connectivity-networking/essential-network-settings-and-tasks-in-windows).

У PowerShell від адміністратора, використовуючи точну назву інтерфейсу:

```powershell
Set-DnsClientServerAddress -InterfaceAlias "Wi-Fi" -ServerAddresses @("1.1.1.1", "1.0.0.1", "2606:4700:4700::1111", "2606:4700:4700::1001")
```

IPv6-адреси використовуйте за наявності робочого IPv6. Саме задання IP не гарантує шифрування: у Windows 11 окремо перевірте параметри DoH та дозволеного fallback. Доступність залежить від версії й політик.

Якщо початково DNS надходив автоматично, поверніть його:

```powershell
Set-DnsClientServerAddress -InterfaceAlias "Wi-Fi" -ResetServerAddresses
```

Попередню ручну конфігурацію потрібно відновити явно. Параметри команди описані в [Set-DnsClientServerAddress](https://learn.microsoft.com/en-us/powershell/module/dnsclient/set-dnsclientserveraddress).

### macOS

Відкрийте **System Settings → Network → потрібний сервіс → Details → DNS**. Додайте адреси й застосуйте зміни. Для повернення до автоматичних DNS приберіть додані вручну записи. [Інструкція Apple](https://support.apple.com/guide/mac-help/change-dns-settings-on-mac-mh14127/mac)

Через Terminal, використовуючи точну назву сервісу:

```bash
sudo networksetup -setdnsservers "Wi-Fi" 1.1.1.1 1.0.0.1
```

Скидання ручного списку для сервісу, який початково використовував автоматичні DNS:

```bash
sudo networksetup -setdnsservers "Wi-Fi" empty
```

Це не налаштовує DoH. Профілі та VPN можуть створювати додаткові resolver: перевірте `scutil --dns`. Синтаксис утиліти доступний локально через `man networksetup`.

### Роутер: дві різні настройки

У роутері можуть бути окремо **upstream DNS** — кого він запитує сам або як forwarder — та **DNS, який роздається LAN-клієнтам** через DHCP й IPv6 RA/DHCPv6.

Якщо клієнтам видається адреса роутера, вони звертаються до нього. Якщо видається `1.1.1.1`, його DNS-forwarder обходиться. Зміна WAN DNS не на кожній моделі змінює обидва механізми.

Після зміни клієнтам може знадобитися оновити DHCP-оренду або перепідключитися. Власний DoH браузера, ручні DNS та VPN можуть продовжувати використовувати інший маршрут. DNS, отриманий через IPv6, також не зникає лише від зміни IPv4 DHCP.

## Як вибрати публічний resolver

Публічний DNS-провайдер отримує запити, які раніше міг обробляти resolver провайдера доступу. Це зміна сторони, якій ви довіряєте.

| Сервіс | IPv4 стандартного профілю | Особливість |
| --- | --- | --- |
| Cloudflare | `1.1.1.1`, `1.0.0.1` | Стандартний профіль без контентної фільтрації; окремі профілі Families |
| Google Public DNS | `8.8.8.8`, `8.8.4.4` | Публічний resolver із DNSSEC і зашифрованими транспортами |
| Quad9 | `9.9.9.9`, `149.112.112.112` | Захищений профіль із блокуванням відомих шкідливих доменів |

У [Cloudflare](https://developers.cloudflare.com/1.1.1.1/ip-addresses/), [Google](https://developers.google.com/speed/public-dns/docs/using) та [Quad9](https://docs.quad9.net/services/) є різні профілі й способи підключення. Профілі одного сервісу можуть відрізнятися фільтрацією, DNSSEC та ECS.

Оцінюйте журналювання та строки зберігання, потрібну фільтрацію, доступність у своїй мережі, підтримку IPv6 і шифрування. Перевірте також EDNS Client Subnet: цей механізм може передавати частину мережевого префікса клієнта upstream. Єдиний «найшвидший DNS для всіх» не враховує ваше розташування й маршрут.

Дві адреси DNS не обов’язково означають «перша завжди, друга лише при аварії». Клієнти можуть перемикатися або виконувати запити паралельно. Якщо один сервер фільтрує домен, а інший ні, результат буде непослідовним. Для узгодженої політики використовуйте адреси одного профілю або однаково налаштовані власні resolver.

Низька DNS-затримка не дорівнює швидкості завантаження сайту: після визначення адреси час витрачається на з’єднання, серверну обробку й передавання даних.

## Звичайний DNS, DoT, DoH і DNSSEC

**DNS over HTTPS (DoH)** передає DNS-запити всередині зашифрованого HTTPS-з’єднання — з тією самою технологією захисту, яку браузер використовує для відкриття HTTPS-сайтів. Навіщо це потрібно, найкраще видно в порівнянні зі звичайним DNS.

### Звичайний DNS: запит у відкритому вигляді

Коли браузеру потрібна IP-адреса `codebyme.de`, він може звернутися через систему до DNS-сервера, отриманого від роутера або заданого вручну. У звичайному DNS запит і відповідь передаються без шифрування через UDP або TCP на порт `53`.

Це має кілька наслідків:

- **Домен видно в мережі.** Провайдер та інші учасники, які можуть спостерігати цей трафік, бачать запитане ім’я. Воно може належати сайту, рекламному сервісу або програмі, яка працює у фоні. Шлях сторінки на кшталт `/blog/dns-guide` у DNS-запиті не передається.
- **Відповідь можна відфільтрувати.** DNS-сервер провайдера може замість адреси заблокованого домену повернути помилку або адресу заглушки.
- **Запит і відповідь можна підмінити на шляху.** Наприклад, це може зробити зловмисник, який контролює точку доступу Wi-Fi або іншу ділянку мережі. Звичайний DNS сам по собі не захищає канал від такого втручання.

TCP у звичайному DNS використовується не лише для перенесення зон. Клієнт може повторити запит через TCP після обрізаної UDP-відповіді. Заблокований TCP/53 здатен спричинити ситуацію «маленькі відповіді працюють, частина інших запитів — ні». Це докладніше описано в [RFC 7766](https://www.rfc-editor.org/rfc/rfc7766).

### DoH: DNS усередині HTTPS

З DoH браузер або системний клієнт встановлює HTTPS-з’єднання з вибраним DNS-сервісом, наприклад Cloudflare чи Google, і передає запит через нього. Зазвичай це порт `443`. TLS шифрує обмін і дозволяє перевірити, що клієнт підключився до потрібного сервера.

Для провайдера це HTTPS-з’єднання: він бачить адресу DNS-сервісу та параметри передавання, але не може прочитати запитане доменне ім’я з його зашифрованого вмісту. Учасник публічної Wi-Fi-мережі також не може непомітно замінити DNS-відповідь усередині правильно перевіреного TLS-з’єднання.

Якщо блокування реалізовано через DNS провайдера, звернення через DoH до іншого resolver, який повертає справжню відповідь, може відновити доступ до сайту. Водночас DoH-сервіс можна впізнати за його адресою й заблокувати саме з’єднання до нього. Спільний із вебсайтами порт `443` не робить DoH невідрізнимим або невразливим до блокування.

| Характеристика | Звичайний DNS | DNS over HTTPS |
| --- | --- | --- |
| Шифрування каналу | Відсутнє | TLS / HTTPS |
| Типовий порт | UDP або TCP `53` | `443` |
| Що видно з DNS-трафіку | Запитані імена та відповіді | Адресу DoH-сервісу й метадані з’єднання; вміст зашифрований |
| Підміна відповіді на шляху | Сам канал її не запобігає | TLS захищає від непомітної підміни за правильної перевірки сервера |
| DNS-фільтр провайдера | Діє, якщо запит обробляє його resolver або перехоплюється на шляху | Можна обійти через доступний сторонній resolver без цього фільтра |

Сам вибраний DNS-сервіс продовжує бачити запити. Захищений канал до нього не означає, що всі його звернення до авторитетних серверів також зашифровані. Протокол описаний у [RFC 8484](https://www.rfc-editor.org/rfc/rfc8484).

### DoT: окремий TLS-канал для DNS

**DNS over TLS (DoT)** також шифрує DNS-запити, але передає їх без HTTPS, безпосередньо через TLS — зазвичай на TCP-порт `853`. Його використовують, зокрема, системні resolver та роутери. З погляду приховування вмісту запитів від провайдера він вирішує ту саму задачу, а окремий порт дозволяє простіше визначити й обмежити такий трафік. Протокол описаний у [RFC 7858](https://www.rfc-editor.org/rfc/rfc7858).

### DNSSEC: перевірка даних

**DNSSEC** дозволяє перевіряти підписи та ланцюжок довіри, включно з автентифікованим запереченням існування запису. Він не приховує імена, не замінює HTTPS і не підписує довільну непідписану зону. Важливі записи `DS`, `DNSKEY`, `RRSIG` та механізми `NSEC/NSEC3`. Вступ — у [RFC 4033](https://www.rfc-editor.org/rfc/rfc4033).

### Bootstrap: адреса самого DoH-сервера

DoH задають URL, наприклад `https://cloudflare-dns.com/dns-query`. Але для HTTPS-з’єднання спочатку потрібна IP-адреса `cloudflare-dns.com`.

Програма може використати вбудовану адресу, кеш, окремі bootstrap-сервери або системний DNS. Спосіб залежить від реалізації. Тому ввімкнення DoH не є обіцянкою, що пристрій ніколи не зробить жодного іншого DNS-запиту.

Для DoT також важлива перевірка TLS-сертифіката за правильним іменем. Просте підключення до порту 853 без автентифікації сервера не дає тієї самої гарантії захисту.

## DNS безпосередньо у браузері

Браузер може виконувати запити через власний DoH, тоді як `ssh`, пакетний менеджер та інші програми продовжують використовувати системний resolver.

![Окремі маршрути DNS: CLI використовує системний resolver, браузер із власним DoH звертається до вибраного сервісу через HTTPS. Подальше підключення до сайту відбувається окремо](/blog-images/dns-browser-paths.svg)

Це дозволяє змінити DNS для браузера без зміни параметрів інших програм і зазвичай без адміністративних прав, якщо немає обмежень організації. Водночас такий маршрут може обійти локальну DNS-фільтрацію або порушити доступ до внутрішніх імен.

### Firefox

Відкрийте `about:preferences#privacy` та знайдіть **DNS over HTTPS**. Назви залежать від мови інтерфейсу.

| Рівень | Практичний зміст |
| --- | --- |
| Default Protection | Firefox вирішує, коли застосовувати DoH, враховуючи мережу, VPN, політики та інші умови |
| Increased Protection | Використовує вибраний DoH-сервіс, але допускає повернення до системного DNS при проблемах |
| Max Protection | Вимагає зашифрованого DNS; при недоступності показує попередження замість тихого fallback |
| Off | Вимикає власний DoH Firefox; системний DNS може залишатися зашифрованим окремо |

Можна вибрати сервіс або задати власну DoH-адресу. Для експерименту з явно вибраним resolver без тихого fallback використовуйте Max Protection і перевірте статус. Вручну додані винятки можуть змінити поведінку для конкретних сайтів.

У `about:networking#dns` доступна діагностика DNS-кешу; у підтримуваних версіях вона також показує використання TRR/DoH. Поля й назви колонок залежать від версії.

Режими описані в [офіційній довідці Firefox](https://support.mozilla.org/en-US/kb/dns-over-https). Сам увімкнений перемикач ще не підтверджує, що кожен запит конкретного сеансу пішов через DoH.

### Chrome та Chromium-браузери

У Chrome відкрийте `chrome://settings/security` та знайдіть **Use secure DNS**. Для зміни resolver виберіть провайдера або введіть власну DoH-адресу.

У режимі поточного провайдера браузер може спробувати захищене підключення до сумісного сервісу, але це не обов’язково змінює сам сервіс. Автоматичний режим може допускати незашифрований fallback. За вибору власного провайдера Chrome не повертається автоматично до незашифрованого режиму. На керованих пристроях можливість може бути недоступною. [Довідка Chrome](https://support.google.com/chrome/answer/10468685?hl=en&co=GENIE.Platform%3DDesktop)

В Edge знайдіть **Secure DNS** через пошук у Settings. Не переносіть поведінку Chrome на кожну Chromium-збірку: перевіряйте її режими й політики. Microsoft визначає для Edge `automatic` із fallback та `secure` без незашифрованого fallback у [документації DnsOverHttpsMode](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/dnsoverhttpsmode).

Приклади DoH endpoint:

```text
https://cloudflare-dns.com/dns-query
```

```text
https://dns.google/dns-query
```

```text
https://dns.quad9.net/dns-query
```

Це альтернативи: виберіть одну, а не вставляйте всі рядки в одне поле. Адреси опубліковані в документації [Cloudflare](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/), [Google](https://developers.google.com/speed/public-dns/docs/doh) та [Quad9](https://docs.quad9.net/services/).

### Перевірка саме браузера

`dig @1.1.1.1 ...` перевіряє сервер `1.1.1.1`, а не маршрут браузера. Перевіряйте статус DoH, DNS-діагностику та мережевий журнал браузера. Для поглибленого аналізу зіставляйте їх із захопленням трафіку й відомими адресами endpoint.

Відсутність UDP/53 сама по собі не доводить DoH: могла спрацювати кешована відповідь, DNS міг піти через TCP, DoT або VPN. DNS-пакети від іншої програми також не доводять, що браузер не використовує DoH.

Сайти перевірки DNS-leak зазвичай створюють унікальні імена та визначають, які resolver звернулися до їхніх авторитетних серверів. Це допомагає перевірити вибір resolver, але не є повним доказом шифрування каналу від браузера до нього.

## DNS-блокування та приватність

Провайдер може блокувати доступ до сайту через свій DNS: замість справжньої адреси повертати помилку або адресу сторінки-заглушки. У такому випадку допомагає DoH або DoT до іншого resolver, який не блокує цей домен. Запит проходить зашифрованим каналом, тому провайдер не може просто прочитати його й підмінити DNS-відповідь на шляху. Сам вибраний DNS-сервіс при цьому має бути доступним із вашої мережі.

Проста заміна адреси DNS, наприклад на `8.8.8.8`, теж може спрацювати, але звичайні запити залишаються відкритими. Провайдер може бачити їх і перехоплювати звернення на порт 53. DoH та DoT прибирають саме цю можливість читати або змінювати вміст запитів у мережі доступу. Якщо ж блокується безпосередньо IP-адреса сайту, зміна DNS такого блокування не усуне.

Шифрований DNS корисний і без блокувань. Звичайні DNS-запити розкривають домени, до яких звертаються браузер та інші програми. З DoH або DoT до стороннього сервісу провайдер доступу вже не може отримати цей перелік простим читанням DNS-трафіку. Сам вибраний resolver запити бачить, тому його політика приватності має значення.

Водночас провайдер продовжує бачити IP-адреси з’єднань, час та обсяг передавання. Ім’я сайту також може бути видно в незашифрованому SNI, якщо з’єднання не використовує ECH. Отже, шифрування DNS зменшує кількість доступної провайдеру інформації, але не робить відвідування сайтів невидимим.

### VPN, внутрішні імена й captive portal

VPN може передавати власні DNS та маршрути. Власний DoH браузера може обійти внутрішній DNS VPN, але це ще не означає вихід трафіку **поза тунель**: HTTPS-з’єднання до DoH може йти через VPN. Перевіряйте окремо, хто розв’язує ім’я та яким маршрутом іде з’єднання.

Для `git.corp.example`, відомого лише внутрішній зоні, публічний resolver може повернути `NXDOMAIN`. Потрібні корпоративний resolver та правильний split DNS. Аналогічно, зовнішній DoH може обходити Pi-hole або іншу домашню DNS-фільтрацію.

У гостьовій мережі з captive portal спочатку може знадобитися пройти сторінку входу. Суворий DoH і заблокований endpoint здатні завадити визначенню імен до авторизації. Автоматичні режими браузерів можуть спеціально враховувати такі мережі.

## Діагностика і шпаргалка

Розділяйте рівні: чи працює мережевий маршрут, чи є DNS-відповідь, чи доступна потрібна адреса та чи проходить TLS.

### Типові відповіді

| Результат | Що перевіряти |
| --- | --- |
| `NOERROR` із відповіддю | Далі перевіряйте повернуту адресу та підключення |
| `NOERROR` без потрібних записів | Ім’я може існувати без запитаного типу; дивіться також CNAME і authority |
| `NXDOMAIN` | Імені немає за цією відповіддю; перевірте написання, split DNS і фільтрацію |
| `SERVFAIL` | Можливі проблеми DNSSEC, upstream або делегування |
| `REFUSED` | Сервер відмовив, наприклад через політику доступу до рекурсії |
| Timeout | Немає відповіді в межах очікування; це не DNS-код і не доказ відсутності імені |

### Перевірити адресу

```bash
dig codebyme.de A +noall +answer +comments
```

Окремо IPv6:

```bash
dig codebyme.de AAAA +noall +answer +comments
```

`AAAA` може існувати, навіть якщо IPv6-маршрут клієнта зламаний. DNS повідомив адресу, але з’єднання з нею не встановлюється. Порівняння через curl:

```bash
curl -4 -I https://codebyme.de
```

```bash
curl -6 -I https://codebyme.de
```

Помилка другого запиту в мережі без IPv6 очікувана. Не видаляйте `AAAA` домену лише тому, що один клієнт не має IPv6-підключення.

### Порівняти resolver

```bash
dig @1.1.1.1 codebyme.de A
```

```bash
dig @8.8.8.8 codebyme.de A
```

Різні IP не завжди означають підміну: можливі CDN, балансування та різний стан кешу. Порівнюйте також `status`, TTL, CNAME-ланцюжок та авторитетну відповідь.

### Перевірити авторитетний сервер

```bash
dig codebyme.de NS +short
```

Підставте ім’я одного з отриманих серверів замість `ns.example.net`:

```bash
dig @ns.example.net codebyme.de A +norecurse
```

`ns.example.net` — позначення для заміни, не справжній сервер `codebyme.de`. Прапорець `aa` у відповіді вказує на авторитетність; сам `+norecurse` не робить довільний сервер авторитетним.

### TCP і DNSSEC

Запит через звичайний TCP/53:

```bash
dig +tcp @1.1.1.1 codebyme.de A
```

Запросити DNSSEC-дані у validating resolver:

```bash
dig @1.1.1.1 codebyme.de A +dnssec
```

`+dnssec` встановлює DO-біт і просить DNSSEC-дані, але не перетворює `dig` на локальний валідатор. Прапорець `ad` повідомляє про перевірку resolver; довіра до цього прапорця потребує довіреного каналу до resolver. Відсутність `ad` сама по собі не доводить поломку: зона може бути непідписаною.

Порівняльний запит із вимкненою перевіркою на resolver, який підтримує CD-біт:

```bash
dig @1.1.1.1 codebyme.de A +dnssec +cdflag
```

Якщо без CD отримуєте `SERVFAIL`, а з ним — дані, перевіряйте DNSSEC: `DS` у батьківській зоні, ключі, підписи й час. Це діагностика, а не рекомендація постійно вимкнути валідацію.

### Очистити потрібний кеш

У Linux із `systemd-resolved`:

```bash
sudo resolvectl flush-caches
```

У PowerShell:

```powershell
Clear-DnsClientCache
```

На сучасних macOS поширена така процедура:

```bash
sudo dscacheutil -flushcache
sudo killall -HUP mDNSResponder
```

Кеш браузера очищається окремо його діагностичними засобами або перезапуском. Системна команда не очищає кеш публічного resolver та не виправляє запис на авторитетному сервері.

### Побачити незашифрований DNS

На Linux із `tcpdump`:

```bash
sudo tcpdump -ni any 'udp port 53 or tcp port 53'
```

Такий дамп може містити імена з DNS-запитів. DoH за цим фільтром не видно; захоплення на фізичному інтерфейсі при VPN може показувати лише тунель. Обирайте точку спостереження відповідно до задачі.
